# Pi → DSH 架构映射标准

本标准是 pi2dsh 判断“理论上能否兼容、代码是否已经实现、真实插件是否已经证明”的唯一
口径。它替代过去彼此平行的 compatibility matrix、三轴审计和五级账本组织方式；旧数据
继续保留，但全部成为同一架构总账的输入或视图。

## 一套总账，三个视图

```text
Pi 完整接口清单                    DSH 完整模块清单
111 条 ABI + 嵌套接口              45 个模块 + 公开 seam
        │                                  │
        ▼                                  ▼
Pi 能力契约      ──理论映射──▶      DSH 承载机制
        │                                  │
        └────────── 映射契约 ──────────────┘
                           │
                           ▼
                   真实插件验证记录
                           │
                           ▼
              架构模型 / 验证矩阵 / 架构结论
```

结构化事实只维护在 [`architecture-ledger.json`](architecture-ledger.json)。由它生成：

- [`architecture-mapping-matrix.md`](architecture-mapping-matrix.md)：理论架构模型；
- [`plugin-validation-matrix.md`](plugin-validation-matrix.md)：真实插件实践记录；
- [`dsh-architecture-conformance.md`](dsh-architecture-conformance.md)：当前架构结论。

逐接口的当前运行时行为仍由 `src/compatibility.ts` 提供，并生成
[`capabilities/`](capabilities/README.md)。它不再独立代表架构结论，而是总账里的 Pi
叶子接口与当前实现证据。

## 第一部分：理论架构模型

### Pi：接口必须归入能力契约

Pi 侧采用三层结构：

```text
能力域 → 能力契约 → 具体 ABI / 事件 / context 方法
```

能力契约描述用户目标，而不是简单把相邻 API 装进同一文件。每条 Pi surface 必须恰好
属于一个能力契约；嵌套对象必须继续下钻到可调用方法，桥扩展与 import symbols 单列，
不得混入上游 ABI 分母。

一项能力契约必须能回答：用户要什么、在什么时机介入、读写什么权威状态、生命周期
如何结束、结果在哪里呈现。

### DSH：模块必须归入承载机制

DSH 侧采用同样的三层结构：

```text
架构域 → 承载机制 → subsystem / service / provider / waterfall / event / client slot
```

45 个 subsystem 是完整性边界，不是主叙事。每个模块必须恰好归入一个承载机制；每个
承载机制必须列出仓外插件真正能使用的公开 seam。只有模块名、没有公开插口，不构成
可实现的架构映射。

### 理论映射：比较语义，不比较名字

每个 Pi 能力契约必须恰好对应一条理论映射。映射沿五个维度判断：

```text
用户目标 · 介入时机 · 权威状态 · 生命周期 · 原生呈现
```

理论结果只有四种：

| 理论结果 | 含义 |
|---|---|
| **直接承接** | 一个公开 DSH seam 可以表达完整契约 |
| **组合承接** | 需要多个公开机制组合，但仍保持一套权威状态 |
| **宿主语义翻译** | 用户目标可以保留，但终端与 Web 等宿主表示必须重做 |
| **缺公开 seam** | 正确的数据或决策时机位于仓外插件不可到达的位置 |

“有同名事件”不等于可映射。例如 Pi 的“压缩前替换摘要”需要事前决策通道；DSH 的
“压缩已经开始”事实事件名字再接近，也不能满足同一能力契约。

## 第二部分：实践验证矩阵

理论映射说明应该怎么接，真实插件验证说明实际上有没有接住。每条验证记录必须引用
已有映射 ID，并沿固定五层留下证据：

```text
Pi 插件实际调用
  → pi2dsh 实际翻译
  → DSH 公开 seam
  → DSH 原生权威状态
  → 用户可观察、恢复和回放的结果
```

实践只使用一套五级判定：

| 等级 | 判定 | 标准 |
|---:|---|---|
| 1 | 原生承接 | 直接使用公开 seam，事实进入 DSH 原生状态和界面 |
| 2 | 可靠翻译 | 表示不同但目标完整，没有第二套 runtime 或权威状态 |
| 3 | 旁路完成 | 用户能用，但依赖 sidecar、桥内 store 或自有展示通道 |
| 4 | 降级或缺失 | 时机、数据或控制能力不完整，或只能拒绝/no-op |
| 5 | 宿主专属，不计分 | Pi 终端/CLI 实现不应原样搬进 DSH |

一个插件可以验证多条映射，每条映射独立判级。禁止用“整包通过”掩盖其中某项能力只
达到 3/4 级；也禁止把契约测试、挂载成功或 import 成功当成真实场景验证。

## 第三部分：架构结论

结论由理论映射、实现状态和实践验证共同推导：

| 条件 | 结论 |
|---|---|
| 有合理映射，已实现，真实插件达到 1/2 级 | 已证明成立 |
| 有合理公开 seam，但桥未实现或实现错误 | pi2dsh 欠账 |
| 缺公开 seam，且真实场景与最小复现达到 3/4 级 | 已确认 DSH 缺口 |
| 属于 Pi 宿主实现 | 宿主差异 |
| 理论上可映射但没有真实验证 | 理论可行、尚未实证 |

`DSH-ARCH-*` 只能来自第三行。没有真实消费者、没有倒推权威数据流、没有最小复现时，
只能记“待判定”，不能为了显得完整提前甩给 DSH。

## 强制完整性约束

文档生成检查必须保证：

1. 固定上游版本的每条 Pi surface 恰好属于一个能力契约；
2. 每个能力契约恰好有一条理论映射；
3. 官方 45 个 DSH subsystem 恰好属于一个承载机制；
4. 每条理论映射引用真实存在的 DSH 机制；
5. 每条插件验证引用真实存在的理论映射，等级只能是 1–5；
6. `src/compatibility.ts` 的新增、删除或改名若未同步总账，`pnpm check:docs` 必须失败。

这保证“抽象上能对齐”和“抽象内每个接口能实际落位”同时成立。总数相等但存在错分、
重复或孤立接口，同样算失败。

## 每次开发如何更新

新增或验证插件时，不新写一套说明，只完成同一条链：

1. 找出插件实际使用的 Pi 接口，并引用其能力契约；
2. 读取对应的理论映射和预期 DSH seam；
3. 实现或核对五层真实数据流；
4. 给每条映射分别判级并附契约/E2E 证据；
5. 由规则归因成“成立、桥欠账、DSH 缺口、宿主差异或尚未实证”；
6. 更新结构化总账并重新生成视图。

以后汇报单个插件时，固定回答：它触碰了哪些能力契约、理论上落到哪些 DSH 机制、实际
走到了五层中的哪一层、各项达到哪一级、产生了什么结论。汇报总体时，则按能力契约、
DSH 机制和验证等级聚合同一份总账，不重新翻聊天记录。
