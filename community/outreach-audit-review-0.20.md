## 二、复核方法

从四个被否定的桶各抽样（一半取热度最高、一半按等距抽样以便去偏），共 **185 帖**，
逐帖读原文重判，判据只有一条：

> **这个人要的"结果"，今天装上我们的东西能不能拿到？**
> 而不是"DSH 那个坏掉的组件我们能不能修好"。

分级：`yes_today`（现成已验证的包直接给结果）/ `yes_if_built`（ABI 扛得住，
需要写东西）/ `no_dsh`（真需要 DSH 自己的件或不存在的扩展点）/ `no_other`
（外部服务、他人展示帖、噪音）。

### 判错的方式只有一种，重复了上百次

流水线把**用户描述的手段**当成了**用户要的结果**。用户在帖子里指认了 DSH 的某个
符号或文件，流水线就据此结案为"DSH 核心缺陷，我们修不了"，从不追问"这个结果有
没有第二条路"。三条自验实例：

- **#473**（↑7，自建网关 compat）：`llm-pi-ai` 的 settings schema 只认两个 compat
  字段，`supportsDeveloperRole` 被静默丢弃，火山方舟/Kimi Coding 这类端点的推理
  路由完全不可用。他要的是**网关能用**。这正是 `examples/gateway-compat` 已实测
  且进了发版回归的场景。判定：dsh_core_bug ❌
- **#588**（文本模型贴图）：文本主模型 + 独立视觉模型的私有部署，图片在 host
  admission 层就被拒。他描述的期望流程与我们 0.9.0 起的**伴生路由**几乎一字不差。
  判定：dsh_core_bug ❌
- **#455**（↑5，子代理凭据）：DSH 原生子代理继承"创建时默认模型"而非会话当前模型，
  第三方 provider 下必报 no API key。`@tintinweb/pi-subagents` 经桥的三级模型解析
  正是跟随会话实时选择——同类问题结构上不成立。判定：dsh_core_bug ❌（对 DSH 原生
  子代理这句话是对的，但对这个人的诉求是错的）

### 真正无解的部分确实存在

约占三成，集中在四处，共同点是**权威状态或渲染座位在 DSH 手里**：
多根工作区 + 沙箱写白名单、原生 adapter 的序列化缺陷（如未配对 UTF-16 代理项）、
ACP 参数校验、Web 设置页/渲染座位（Mermaid、数学公式、RTL、会话删除）。
回帖时必须如实说"这件 DSH 自己的件我们修不了"。

## 六、结构性问题（不改就会重犯）

1. **判据错**：以"能否修复 DSH 组件"结案，而非"用户的结果有没有第二条路"。
   修法：凡理由含"属 DSH 核心 / 上游修复"，强制回答第二条路，答不出才结案。
2. **单标签绑死**：一旦贴上 `ui_tui`，理由就固定为"我们的 TUI 修不了 Web"，
   桥的**浏览器半边**（client 插件 / Settings section / 侧栏 tab）在全部理由中
   一次都没被考虑过——而 dsh-work-x 的 Web MCP tab 正是走这条路。
3. **产品线白名单**：7 条线之外的 491 条直接不看，`hermes_memory` 整线因此漏掉
   （抽样 5 条里 3 条是 yes_today）。
4. **展示帖一刀切**：Pi 生态作者现身 DSH 社区（如 #132）与纯软文被同一句
   "showcase" 抹平——前者恰恰是最该接触的人。
5. **模型档次与流程**：关键判断用了最便宜的模型且关闭思考，末段还不读原文。
6. **快照会馊**：语料是 8-23 的快照，三天新增 **421** 帖（社区一个月 4149 帖，
   约 140 帖/天）。一次性大审计的结论几天就过期，必须转成增量盯帖。
